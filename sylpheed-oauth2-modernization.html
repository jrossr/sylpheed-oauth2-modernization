Modernizing Sylpheed OAuth2 — and the Cloud Wall That Stopped the Test

A source-level modernization of Sylpheed’s unfinished OAuth2/XOAUTH2 path on AlmaLinux 9.8: PKCE, public-client authentication, secure state generation, refresh-token caching and rotation, safer logging, protocol integration, and helper-process failure handling. The code built successfully. The final Microsoft test did not fail in C, TLS, IMAP, or OAuth protocol code—it stopped at Microsoft’s app-registration/tenant enrollment process.

1. Why This Work Started

The original goal was simple: configure a Microsoft Hotmail/Outlook account in Sylpheed. The existing Sylpheed 3.7 installation already handled ordinary mail and Gmail after a separate TLS SNI compatibility fix.

Microsoft IMAP connectivity itself worked. Sylpheed established TLS 1.3 to outlook.office365.com:993, validated the certificate and received the server capability list:

* CAPABILITY IMAP4 IMAP4rev1 AUTH=XOAUTH2 LOGINDISABLED ...

LOGINDISABLED meant the traditional username/password LOGIN path could not authenticate. An application password could not fix a mechanism the server refused to offer. Microsoft required XOAUTH2.

Not a TLS problem: SNI worked, TLS worked, certificate verification worked, hostname validation worked and the Microsoft IMAP server answered normally. Authentication policy was the barrier.

2. Protect the Known-Good Client

The working 3.7 source and installed mail client were deliberately left untouched. OAuth work was done in a separate upstream Git tree based on Sylpheed 3.8.0beta1. The experimental build was never installed over the working 3.7 system.

3. What Upstream Already Had

Upstream contained real but incomplete OAuth machinery: libsylph/oauth2.c, XOAUTH2 paths in IMAP/POP3/SMTP, syl-auth-helper, an oauth2.ini.sample, browser authorization-code handling, token parsing, and account fields for access token, refresh token and expiry.

The SASL form was already essentially:

base64("user=" + username + "\x01auth=Bearer " + access_token + "\x01\x01")

The problem was not absence of OAuth code. It was an unfinished lifecycle and an older OAuth model.

5. Getting the Upstream Tree to Build

The Git tree used autogen.sh. Its Automake commands were pinned to 1.15 while Alma supplied 1.16, so the experimental tree was adjusted to use the available toolchain. Configuration initially stopped because the GPGME Autoconf macro was absent; the matching development package supplied it. The matching libcurl development package was also installed for the OAuth helper.

Configuration then detected GLib 2.68.4, GTK+ 2.24.33, GPGME, OpenSSL and libcurl, and generated a build that included syl-auth-helper.

6. PKCE and Public-Client Authentication

A desktop application cannot safely hide a compiled-in client secret. The test implementation therefore added PKCE. It generates 32 cryptographically random bytes, Base64URL encodes the verifier, computes SHA-256 over it, and Base64URL encodes that digest as the challenge.

code_challenge=<SHA256-base64url(verifier)>
code_challenge_method=S256

The token request then sends:

grant_type=authorization_code
code_verifier=<original verifier>

client_secret became optional, allowing a proper public-client configuration.

7. Secure Randomness and OAuth State

On the Alma/Linux test implementation, PKCE and OAuth state use getrandom(2). The helper handles interrupted calls and partial reads rather than assuming one call fills the buffer. The older state generator based on g_random_int() was replaced with 32 random bytes encoded as Base64URL. Failure to obtain secure randomness aborts the authorization attempt.

8. Refresh Tokens: Completing the Missing Lifecycle

Upstream had refresh-token-related fields but did not actually complete the lifecycle. Rather than spreading expiry and persistence logic through Sylpheed’s account preferences, the test branch uses a helper-owned model: whenever a protocol needs OAuth authentication, syl-auth-helper obtains a usable access token. If a private cached refresh token exists, the helper performs the refresh grant first.

The cache is per account under Sylpheed’s configuration directory. The writer uses a temporary file, restricts permissions to the user, writes the token and atomically renames the file into place.

Refresh failure policy:

  • Success: return access token and save a rotated refresh token if supplied.
  • Explicit invalid_grant: remove the stale cache and fall through to browser authorization.
  • Transient/network/other failure: preserve the cached refresh token and fail the attempt rather than destroying credentials or repeatedly launching a browser.

9. IMAP, POP3 and SMTP Integration

Each protocol now frees its old in-memory access token and asks the helper for a current one immediately before OAuth authentication:

g_free(account->token);
account->token = NULL;
oauth2_get_token(user, &account->token, NULL, NULL);

if (!account->token) {
    /* authentication cannot proceed */
}

This keeps refresh-token ownership out of the mail protocol implementations and avoids requiring each protocol to understand expiry.

10. Secret-Bearing Debug Output Removed

Review found debug paths capable of exposing authorization codes, token response bodies, helper stdout, HTTP POST bodies, redirect data or XOAUTH2 SASL payloads. These were removed or redacted. Refresh tokens are not intentionally printed to stdout; helper stdout is reserved for the access token requested by the parent process.

Development note: historical checkpoint files can contain earlier code. A security grep of the development tree must distinguish active source from backups.

11. Helper Exit-Status Bug

A late audit found that oauth2_get_token() used g_spawn_sync() and captured status without checking whether the helper actually exited successfully. A successful spawn is not an OAuth success.

if (!g_spawn_check_exit_status(status, &error)) {
    g_warning("OAuth2 helper failed: %s\n",
              error ? error->message : "unknown error");
    g_clear_error(&error);
    g_free(out);
    return -1;
}

The normal-success path was also corrected to free the helper-output allocation. The affected library rebuilt cleanly with make -C libsylph -j2.

12. Full Build Result

The complete experimental tree was built with make -j2. The OAuth helper, Sylpheed libraries, main executable and plugins linked successfully, translations generated, and the top-level build returned normally.

Result: the OAuth modernization was not stopped by a compiler or linker failure. The full experimental tree built successfully.

After generated Autotools churn was restored, the intentional tracked modification set was limited to:

13. Microsoft Configuration the Client Was Preparing to Use

The upstream sample pointed Microsoft OAuth at the common v2 authorization/token endpoints with a localhost redirect and delegated mail scopes. The intended scope set included offline access plus POP, IMAP and SMTP permissions:

offline_access
https://outlook.office.com/POP.AccessAsUser.All
https://outlook.office.com/IMAP.AccessAsUser.All
https://outlook.office.com/SMTP.Send

Hotmail/Live wildcard sections would also be needed in oauth2.ini; an *@outlook.com rule does not match Hotmail or Live addresses.

14. What Actually Stopped the Live Test

The live test did not stop because XOAUTH2 failed.
It did not stop because PKCE failed.
It did not stop because refresh-token handling failed.
It did not stop because IMAP or TLS failed.

The live OAuth exchange was never reached.

A real authorization attempt required a Microsoft application registration and therefore a client ID. Trying to reach app registration with the existing personal Microsoft account led into Microsoft Entra tenant infrastructure. The account was presented with the “Microsoft Services” tenant but did not have access to it.

The Azure route then led toward obtaining the tenant/subscription context needed for app registration. Enrollment reached payment/card verification, where the bank card was rejected even though the user reported that the same payment methods had long worked for other Microsoft services, including Xbox. The cardholder-name verification became the practical stopping point.

The decision was made not to keep submitting cards or changing valid identity information merely to obtain an OAuth client ID for one consumer mailbox.

Accuracy boundary: this is a successful build report, not a claim of successful end-to-end Microsoft OAuth. No Microsoft app client ID was obtained, so the modified client never reached a live authorization/token exchange.

15. Why the Work Still Matters

The investigation produced useful engineering regardless of the abandoned Hotmail goal: PKCE, public-client behavior, cryptographically strong state on Linux, refresh-token caching and rotation, explicit invalid_grant recovery, protection against transient refresh failures, protocol reauthentication, safer logging, child-process failure handling, and a successful full build.

It also established a clean failure boundary: the source work reached a compilable checkpoint; the provider-side administrative onboarding prevented final validation.

16. Known Limitations Before Calling It Upstream-Ready

  • Windows portability: the secure-random patch currently depends on Linux getrandom(); a portable upstream patch needs a secure Windows implementation.
  • Token parser: the existing response parser is simple and could be hardened.
  • Cache-save errors: stronger reporting/recovery would improve robustness.
  • Provider configuration: Microsoft domain patterns and final settings still require live validation.
  • Microsoft end-to-end test: not performed because app registration/client ID was not obtained.
  • Patch cleanup: experimental checkpoint files must not be included in a real upstream patch series.

17. Development Method

The work was deliberately incremental. Source checkpoints were taken before and after PKCE helpers, PKCE wiring, public-client changes, logging cleanup, cache I/O, HTTP status plumbing, refresh grants, OAuth error parsing, refresh policy, protocol integration, secure randomness, secure state, cleanup paths and helper exit-status handling. A bad edit could therefore be reversed without risking the known-good installed mail client.

18. Bottom Line

Code result: successful.
Full experimental build: successful.
Working Sylpheed 3.7 install: preserved.
Microsoft IMAP/TLS connectivity: successful.
Microsoft app registration/client ID: not obtained.
Live Microsoft OAuth: therefore not reached.

The precise conclusion is not “Microsoft OAuth failed.” It is:

The modified OAuth client built successfully, but the end-to-end Microsoft test was abandoned before authorization because the required Microsoft application registration could not be completed through the available account/enrollment path.
